# 技術構成・インフラ仕様

## 構成
- **Frontend**: React（Vite） -> Vercel
- **Backend**: Python（Django） -> Render Web Service
- **OCR Worker**: Python（Django management command + PaddleOCR） -> Render Background Worker
- **Database**: PostgreSQL（Render Managed DB）
- **Storage**: Cloudinary。レシート画像は `authenticated` アセットとして保存し、公開URLでは配信しない。

## 環境変数（.env）管理
- `SECRET_KEY`: Djangoのシークレットキー
- `DEBUG`: 開発環境ではTrue、本番環境ではFalse
- `DATABASE_URL`: DB接続情報（Render Web Service と Render PostgreSQL が同一workspace・同一regionの場合は internal connection string）
- `PADDLE_PDX_MODEL_SOURCE`: PaddleOCRモデルのダウンロード元（例: `BOS`）
- `PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK`: 複数配布元の事前接続確認を省略する（Renderでは `True`）
- `PADDLE_OCR_VERSION`: 日本語mobileモデルを使うため `PP-OCRv3`
- `PADDLE_ENABLE_MKLDNN`: Paddle 3.xとの互換性を優先して `False`
- `CORS_ALLOWED_ORIGINS`: フロントエンドのURLを許可
- `CSRF_TRUSTED_ORIGINS`: CSRFを許可するフロントエンドURL
- `CLOUDINARY_URL`: Cloudinary接続情報

## 注意点
- `.env` はGitHubにアップロードしない。
- PaddleOCRはWorker側だけで実行し、React側にはOCR実行環境を置かない。
- APIサービスとWorkerサービスが分かれる本番では、レシート画像を両者から読める共有ストレージを設定する。
- Workerは `cd backend && python manage.py run_ocr_worker --poll-seconds 2` で起動する。
- Render Background Workerは PaddleOCR の常駐メモリを考慮して Standard（2 GB RAM / 1 CPU）を使用する。Starter（512 MB）はモデル読込時のメモリ不足リスクが高いため使用しない。
- 日本語OCRは `PP-OCRv3` mobile detection / recognitionモデルを使用し、モデルはBOSから取得する。
- `CLOUDINARY_URL` は既存Blueprintの同期では追加されないため、デプロイ担当者が `amber-api` のEnvironmentへ手動登録する。`amber-ocr-worker` はBlueprintの `fromService` で同じ値を参照する。
- レシート原本の一時ダウンロードURLは5分で失効し、APIレスポンスには含めない。
- 本番環境では `DEBUG=False` にする。
- Vercel側には `VITE_API_BASE_URL=https://<Render Web Service URL>/api` を設定する。
- Render側には Vercel のURLを `FRONTEND_ORIGIN` / `CORS_ALLOWED_ORIGINS` / `CSRF_TRUSTED_ORIGINS` に設定する。
- Render PostgreSQL の internal connection string は、同一workspace・同一regionのRenderサービスからのみ利用する。
